# 分类之后怎样维护

分类只是入口，不等于处理完成。“已有 PR”只说明存在候选修复，不表示已审查、已验证或已合入。当前 101 条均有分类，但处理尚未全部完成。

## 本地 Agent 的后续责任

1. 联网刷新 issue、PR/head、目标分支与讨论；旧状态有日期和来源，不沿用过期的“最新”。
2. 按同一问题/PR 合并审查，阅读真实 diff，确认是否覆盖原问题、是否与其他 PR 重叠、是否引入无关改动。
3. 复用与当前源码身份相符的现有测试或 CI 证据。链接/拼写/帮助文本采用最小静态或主机检查，不统一升级为 NPU 全量回归。
4. 没有可用修复时，处理本地能够完成的脚本、文档和接口修改，形成可审查补丁；已有充分候选时避免重复实现。
5. 将真正需要 SDK/设备的问题连同固定 PR head、最小输入和验收要求整理给服务器。环境缺失记录具体条件，不让单个问题卡住清单。
6. 回收结果并核对证据边界；将“候选已验证”“修复已合入”“可关闭”分别记录。用户暂缓远端操作期间只准备补丁和关闭说明。

## 台账必须显示什么

每条有：原问题、当前分类、审查阶段、实际差异结论、关联 PR/head、已有测试与边界、下一步、负责方、更新日期和关闭依据。
不能一直停留在统一的“有 PR”备注。当前 CSV/JSON 已加入 review_stage、evidence_level、last_review_date，后续审查写入 PROGRESS.json 后再生成清单，不覆盖回初筛状态。
